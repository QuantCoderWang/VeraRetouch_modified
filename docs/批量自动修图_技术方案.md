## 1. 需求与验收标准

### 1.1 用户需求原话（要点整理）

1. 在所有功能页最后**增加一个"批量自动修图"页签**；
2. 功能几乎与"一键自动修图"相同，但**不拖图片**：只需**选择待修图文件夹**和**输出文件夹**；
3. **不用选输出格式**：输入什么格式输出什么格式（固定"跟随输入格式"）；
4. "模型分析与修图计划"文本继续保留；
5. **每一张图处理时，用这张图的名字新建一个 txt 文件**，保存当时生成的模型分析与修图计划；
6. 设置完成后**自动完成所有图片修图**，保存记录，**系统提醒完成任务**；
7. **保留单图修图进度条**，**新增整体任务进度条**；进度计算依据单张图耗时估算进度（具体方案本方案定，见 §4.5）；
8. 页面设计风格同其他页面，可大量挪用"一键自动修图"的界面与代码。

### 1.2 验收标准（开发完成的判定）

- [ ] 新页签"批量自动修图"位于四页签之后（第 5 位）；
- [ ] 选择输入/输出两种文件夹 → 点"开始批量修图"即全自动完成全部图片；
- [ ] 每张图输出：**同名图片文件（跟随输入格式）+ 同名 .txt（该图的模型分析与修图计划原文）**；
- [ ] 全批结束有**汇总记录文件**与**系统完成提醒**；
- [ ] 界面上同时可见：单图进度条 + 总体进度条（含"第 X / Y 张 · 正在处理 …"与预计剩余时间）；
- [ ] 单张失败不中断批次（失败图片计入汇总继续下一张）；
- [ ] **长批次内存稳定**（≥ 30 张混合批次，进程内存不随张数单调上涨）；
- [ ] 现有四页签行为零回归（`tests/ui_smoke_test.py` 全绿）。

## 4. 技术方案

### 4.1 总体数据流（与一键自动修图的关系）

```
批量页签           ——100% 复用——▶  VeraRetouchRunner.run(mode="auto", …)
（逐张字循环）                        ↑ 模型常驻内存（与四页签同一实例）
   ↓ 每张图                           ↑ 单图进度条走既有流式逻辑
out = runner.run("auto", img_path)    ← per_image_progress
   ↓
save_result(out_pil, text, out_dir_每张的工作目录, fmt_key="auto",
            src_path=img_path)        ← 复用现有导出（"跟随输入格式"逻辑现成）
   ↓
重命名/移动到：输出文件夹/<原名><原扩展名>    +  输出文件夹/<原名>.txt
   ↓ 更新汇总 & 两个进度条 & 预览图
```

- `save_result` 的 `fmt_key="auto"`、`src_path=输入路径` 已是现有能力（导出格式那轮交付），**输入什么格式出什么格式直接复用**；
- 分析文本 `text` 来自 `runner.run` 返回值，与页签文本框同源，**txt 与界面看到的内容一致**。

### 4.2 文件夹选择：为什么不用网页上传、按钮怎么实现

**决策：不走浏览器上传，走"文本框 + 原生浏览按钮 + 服务器端扫描"。**

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 文本框 + [浏览…] 原生对话框（采用）** | 按钮后台调 PowerShell `FolderBrowserDialog`（Windows 系统自带、零依赖）；选完路径回填文本框；处理仍在**服务端本地磁盘**进行 | ✅ 大量图片不经过浏览器上传（几十张×10 MB 也毫无卡顿）；✅ 能在新处理前先扫描统计；✅ 输出目录原生可写 |
| B. `gr.File(file_count="directory")` 网页文件夹上传 | 浏览器 webkitdirectory 上传到服务端缓存 | ❌ 全部图片先复制一遍（成百 MB 流量）；❌ 输出仍是下载文件而非"写进你指定文件夹"；❌ 不符合"选文件夹"的本意 |

**[浏览…] 实现（已验证原理可行）**：

```python
def _native_pick_dir(title):
    ps = ('Add-Type -AssemblyName System.Windows.Forms;'
          '$d = New-Object System.Windows.Forms.FolderBrowserDialog;'
          f'$d.Description = "{title}";'
          '$r = $d.ShowDialog();'
          'if ($r -eq [System.Windows.Forms.DialogResult]::OK) { $d.SelectedPath }')
    out = subprocess.run(["powershell", "-NoProfile", "-Command", ps],
                         capture_output=True, text=True, timeout=120)
    return out.stdout.strip() or None   # 用户点取消返回 None（不改文本框）
```

已确认的事实支撑：
- **嵌入 runtime 无 tkinter**（以上实测），所以 tkinter `askdirectory` 不可用，PowerShell 方案无此依赖；
- `subprocess`、`powershell.exe` 在所有 Windows 上可用，安装版与源码版行为一致；
- 开发语言层面无新依赖（不新增任何 pip 包）。

> 浏览按钮弹窗是用户自己机器上的会话进程，桌面可正常显示对话框；`--listen` 远程访问时对话框出现在**服务器所在机器**（文档会注明；本应用定位本机使用，无影响）。

### 4.3 扫描与过滤规则

```python
IMG_EXTS = {".jpg", ".jpeg", ".png", ".webp", ".bmp", ".tif", ".tiff"}

def scan_images(in_dir: str) -> list[str]:
    # 1) 只取 in_dir 顶层（不递归子目录 —— 三层文件夹容易产出意外结果，V1 从简）
    # 2) 扩展名过滤（大小写不敏感），按文件名排序保证批次顺序稳定
    # 3) 隐藏文件（以 . 开头）排除
    return sorted(p for p in Path(in_dir).iterdir()
                  if p.is_file() and p.suffix.lower() in IMG_EXTS and not p.name.startswith("."))
```

- [扫描图片] 按钮执行后回填统计文案 + 计数（不入库任何东西）；
- 点"开始批量修图"时**内部必然先执行一次扫描**（不依赖用户是否手动扫描）。

### 4.4 保存与记录规则（对应用户第 3、4、5、6 点）

对输入文件夹中的每张图 `输入\<原名>.<ext>`：

| 分析记录 | `输出文件夹\<原名>.txt`（**同名 txt**，内容 = 该图"模型分析与修图计划"全文，UTF-8） |
| 汇总记录 | `输出文件夹\batch_summary.txt`（见下） |

### 4.5 双进度条与耗时估算方案（对应用户第 7 点，本方案的决定）

**结构：每个批量任务一次 click 事件，两个 `gr.Progress` 相应参数并行。**

```python
def batch_handler(in_dir, out_dir, task_progress, img_progress):
    files = scan_images(in_dir)                      # 起点清单
    n = len(files)
    if n == 0: raise gr.Error(i18n.BATCH_ERR_NO_IMG)
    if not os.path.isdir(in_dir): raise gr.Error(i18n.BATCH_ERR_NO_INDIR.format(path=in_dir))
    out_dir = out_dir.strip() or default_out_dir(in_dir)
    os.makedirs(out_dir, exist_ok=True)

    durations = []                                    # 已完成单张耗时（秒）
    ok = fail = skip = 0
    summary_lines = []                                # 汇总行

    for i, img_path in enumerate(files, start=1):
        name = os.path.basename(img_path)
        # ---- 总进度条（时间加权，见下）----
        task_progress(describe_overall(i, n, durations, name), desc=…)
        if already_done(img_path, out_dir):           # 断点续跑：同名输出已存在
            skip += 1; continue
        t0 = time.perf_counter()
        try:
            out_pil, text = runner.run("auto", str(img_path), progress=img_progress)
        except torch.cuda.OutOfMemoryError:              # 显存碎片/OOM：清缓存重试一次
            if torch.cuda.is_available():
                torch.cuda.empty_cache()
            try:
                out_pil, text = runner.run("auto", str(img_path), progress=img_progress)
            except Exception as e2:
                fail += 1
                summary_lines.append(f"{name}  →  ✗ 失败(显存不足重试无效): {e2}")
                gr.Warning(f"{name} 处理失败，已记录，继续处理其余图片")
                durations.append(time.perf_counter() - t0)
                continue
        except Exception as e:                        # 单张失败不中断
            fail += 1
            summary_lines.append(f"{name}  →  ✗ 失败: {e}")
            gr.Warning(f"{name} 处理失败，已记录，继续处理其余图片")
            durations.append(time.perf_counter() - t0)  # 失败耗时也参与平均值
            continue
        # ---- 保存（跟随输入格式 + 同名 txt）----
        save_to(out_dir, img_path, out_pil, text)     # 结果图 + <原名>.txt
        ok += 1
        durations.append(time.perf_counter() - t0)
        # ---- 预览 / 分析文本实时更新（只传"最近一张"，绝不累积历史图）----
        yield (out_image(img_path, out_dir), text, preview_gr, gr.update(value=…))
        # ---- 内存保险丝：低频清理（GC_EVERY=10，详见 §4.9）----
        if i % GC_EVERY == 0:
            gc.collect()
            if torch.cuda.is_available():
                torch.cuda.empty_cache()              # GPU 机顺带清一次显存缓存
        del out_pil                                   # 交还给 GC（下一轮覆盖前不留引用）
        # ---- 预览 / 分析文本 / 单图日志实时更新 ----
        yield (out_image(img_path, out_dir), text, preview_gr, gr.update(value=…))
    # ---- 收尾：汇总文件 + 完成提醒 ----
    write_summary(out_dir, …)
    win_message_beep(); gr.Info(i18n.BATCH_DONE.format(ok=ok, fail=fail, skip=skip, dir=out_dir))
    yield (demo…, summary_text)
```

**总体进度条的"依据单张耗时估算"——三层递进，方案定为 (3)：**

| 候选算法 | 评论 |
|---|---|
| (1) 纯 `i / n` 线性 | 最简单；但总进度条只在整张完成后跳一下，"第 i 张中段"颗粒度不够；且各图耗时不均匀时误差大 |
| (2) 权重 = 训练时估计阶段占比 | 需人工标定权重，CPU/GPU 差异大，不可靠 |
| **(3) 采用：文件内时间段 = 真实单图进度条；整体条 = 时间加权 + 动态 ETA（本方案）** | 见下方 |

```python
def describe_overall(i: int, n: int, durations: list[float], name: str) -> str:
    # —— 时间加权两段式 ——
    elapsed_done = sum(durations)                    # 已完成整张的累计耗时
    omega = durations[-1] if durations else 0.0      # 正在处理的这张已消耗时间
    # 已处理比例 = (完成累计 + 进行中的这一张按"最近平均单张耗时"折算的部分)
    avg = (sum(durations) / len(durations)) if durations else None
    in_progress_credit = 0.0 if avg is None else min(omega / avg, 0.95)
    prog = (elapsed_done + in_progress_credit * avg) / max(n * avg, 1e-9)
    prog = min(prog, 0.99)                           # 最后一格留给最终完成

    # —— ETA ——
    remain_cnt = n - (i - 1)
    eta_secs = remain_cnt * avg if avg else 0.0
    eta = f"{int(eta_secs // 60)}分{int(eta_secs % 60):02d}秒"
    return max(prog, i / n * 0.01), f"{i18n.BATCH_OVERALL_FMT.format(i=i, n=n, name=name, eta=eta)}"
```

**保底（fallback）设计**：

- 5 张图装入前 `durations` 为空 —— ETA 文本改为 `预计时间：统计中…`，总体条按 `i / n` 线性；
- **第一张完成后**：出现均值，进度条与 ETA 开始"时间加权"，误差迅速收缩；后续每张都刷新均值；
- 行为特性：万一某张特别慢（文本生成长尾），总体条会停在较低位置等待真实完成——**不虚标进度**。这与"依据单张耗时估算进度"的要求完全一致，且不引入需要训练方才能保证的数据假设。

**多 Progress 风险清单（开发前要验证）**：
gradio 6 允许一个处理器同时持两个 `gr.Progress` 参数（按形参位置绑定两条进度条），但**两条同时刷新**的前端渲染尚需一次手测确认。保底方案：退化成**一个总体条 + desc 文本显示单张阶段**（`第 3/45 · 文本生成中…`），单图流式进度条仅在"一键自动修图"页签保留。开发时先做双条，若发现两条互相覆盖或闪烁，降级路径已备好。

### 4.7 异常处理与边界情况

| 情况 | 行为 |
|---|---|
| 输入文件夹不存在 / 不可读 | `gr.Error(BATCH_ERR_NO_INDIR.format(path=…))` 弹窗拒绝执行 |
| 输入文件夹零可处理图片 | `gr.Error(BATCH_ERR_NO_IMG)` |
| 输出文件夹不存在 | 自动创建（含所有父级目录） |
| 输出目录在 gradio "cwd/temp" 白名单之外（如 F:\photos\out） | `gr.set_static_paths([out_dir])` 注册为静态路径：浏览器按原文件直接访问（不再报 InvalidPathError，也不把结果复制进缓存）；实际实现于 batch_loop 入口 |
| 输出降噪（暗部噪点放大，方案一·细节回贴） | 每页签的「输出降噪」下拉框（**默认关闭**=模型裸输出；light/medium/strong）随事件传入 batch_loop 的 `denoise_level` 参数；每张渲染后 `denoise_output(alpha)`：亮度 Y 先 NLM(h=10) 强降噪，再按 α（轻0.6/中0.35/强0.15）把原图高频细节层贴回，色度不动（~2.3s/12MP） |
| EXIF 方向 | `save_result` 按源图方向标签把输出像素转正（`bake_exif_orientation`）——PIL 保存不写 EXIF，方向=6/8 的照片若不处理会横竖颠倒（实测 11 张中 1 张） |
| 相机 RAW 输入 | **不支持（2026-11-06 曾实现后按用户决定回退）**：扫描与上传仅收常规格式（jpg/jpeg/png/webp/bmp/tif/tiff）；大疆运动相机 DNG 不在 LibRaw 支持表内、解码不可行的完整经过留档见 `docs/CHANGES_VS_UPSTREAM.md` RAW 回退段 |
| 输出文件夹 = 输入文件夹 | 允许；同名跳过逻辑天然生效（输出名 = 输入名，处理过的自动略过，不会自我覆盖）；但建议分开目录，语义更清晰 |
| 单张失败 | 警告一条、汇总记 ✗、继续处理下一张，不影响总数统计 |
| 处理中关闭控制台 | 即刻退出（无后台残留）；输出的半成品留在输出目录，再次运行自动跳过已完成的 |
| 重复点击"开始批量修图" | 按钮在 click 时即被禁用（`interactive=False`），完成/失败后再启用 |
| 图片实际不可解码（损坏文件） | 并入"单张失败"路径处理 |

## 4.9 内存与长批次稳定性（用户提问：图太多会不会内存溢出？）

**结论：会做防范，但核心防线是"循环纪律"——批处理循环里绝不累积图片对象；`gc` / `torch.cuda.empty_cache()` 只作低频保险丝与 OOM 应急，**不做"每张都清"**（那是负优化）。

### 4.9.1 风险盘点（会不会涨？涨在哪？）

| 项 | 是否随张数增长 | 说明 / 处置 |
|---|---|---|
| **模型权重** | 否（常驻一份） | 与单图修图同额 |
| **单图推理峰值（CPU/显存）** | 否（每张峰值相同，调用结束由 Python/框架释回） | 无需额外处理 |
| **批处理循环对图片对象（PIL/NumPy/张量）的引用** | **若写错是最危险源** | 设计纪律：每张完成即 `del out_pil`（或被下一轮覆盖），**全循环内绝不把 PIL/np/tensor 存入列表**；`summary_lines` 只收纯文本（每张几行字符串，可忽略） |
| **预览用 gradio 服务端缓存** | 是——**磁盘**增长（每张多缓存一张预览图文件），不是内存 | 500 张约额外一份输出体积的临时磁盘；空盘风险极低，程序重启由 gradio 临时目录管理，不影响稳定性 |
| **CUDA 缓存分配器的显存碎片** | 张数大时偶发"碎片化 OOM"（显存总量仍够，但连续块不够了） | 双防线：(a) **低频保险丝**——每 `GC_EVERY=10` 张 `gc.collect()`，GPU 机顺带 `torch.cuda.empty_cache()`；(b) **OOM 捕获重试**——见 §4.9.2 |
| **CPU 内存碎片** | 数百张后极轻微 | 同上低频保险丝覆盖 |

### 4.9.2 显存 OOM 三层防线（GPU 机）

```
第 1 层（常态）：    每张正常收尾释放 + 每 10 张 gc.collect() + empty_cache()
第 2 层（应急）：    本图 try/except torch.cuda.OutOfMemoryError → 先 empty_cache() → 重试一次本图
第 3 层（失败兜底）： 重试仍 OOM → 该图记失败、汇总记录明细、继续下一张（单张牺牲不伤整批）
```

CPU 机没有专门的 OOM 异常类型 → 内存不足走通用 `Exception` 分支（同第 3 层语义）。

### 4.9.3 为什么**不**"每张修完就清缓存"

- `torch.cuda.empty_cache()` 每张都调 = 每张都要向驱动重新申请显存块 → **单张延迟显著增加**，收益极小（正常情况下缓存块本来就在下一张直接复用）；
- Python `gc.collect()` 每张都调 = 全堆扫描 → 批修反而**更慢**，且推理调用内部（无大对象滞留）几乎没有可回收物；
- 正确颗粒度：**低频定时收 + 出事时立刻收**，两层都写进实现（伪代码见 §4.5，`GC_EVERY` 常量集中定义便于将来调整）。

### 4.9.4 设计自检：本方案"不会出现"的溢出形态

- ✗ **不做"全部结果陈列"的界面**——若把 500 张结果图都持在内存里会立即爆内存；用户需求也只要"最近一张"实时预览，全批图片都在磁盘上；
- ✗ **不把每图的图像张量存入汇总**（汇总只收文本行）；
- ✗ **没有预取积压**——批量走逐张循环调用（内部 `DataLoader` 为 `batch_size=1, num_workers=0`）；
- ✗ **不重复加载模型**（同一常驻实例）。

**验收补充（合入 §1.2）**：真模型批量手测 ≥ 30 张（大小混合、成功/失败混合），任务管理器观察进程内存，批次运行中应围绕一个稳定值小幅波动，**不随张数单调上涨**。

## 8. 性能与注意事项

- **内存/显存**：逐张串行处理，模型常驻一份，同"一键自动修图"完全同级，无额外开销；
- **大文件夹体验**：500 张图首扫仅文件名扫描（毫秒级）；总体进度 ETA 第 1 张后即准；
- **通知频率**：绝不逐条弹通知，只终局一条 + 实时预览/文本，避免打扰；
- **Windows 命令规范**：PowerShell 调用使用 `["powershell", "-NoProfile", …]`（避免 profile 干扰与 stderr 报错误判）；路径统一经由 `pathlib.Path`，正反斜杠自动处理。
