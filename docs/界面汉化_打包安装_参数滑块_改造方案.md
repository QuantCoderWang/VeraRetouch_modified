## 1. 现状基线（改造前的关键事实）

- 界面：`app.py`（Gradio 6.14 Blocks），四页签（自动/风格/参数/参考图），标签为"中文 + English"混排，进度提示与报错信息为英文或中英混排。
- 参数修图链路：`Infer_Param_Dataset`（`data/infer_dataset.py:171`）读取 JSON 文件；参数名采用 **Adobe Lightroom 命名**（共 38 个键，`{"键名":{"value":0~100}}` 形式）；
  - 内部归一化：`value / 100.0` → 论文约定区间 **-1.0 ~ 1.0**（`infer_dataset.py` `get_organized_dict`）；
  - **掩码逻辑**（`get_mask_from_path`）：三组——「光调整」「色温与全局色彩」「特定颜色（HSL）」——**若某一组所有参数全为 0，该组控制潜变量被置 0 屏蔽**（模型不感知该组），这是参数界面上"全 0 = 未启用"的依据；
- 依赖规模：`vera_venv` 实测 1.3 GB（含 torch 2.15 CPU、transformers、gradio、diffusers、timm 等）；
- 权重：主模型 `model.safetensors` 2.29 GB + `encoder_renderer.pth` 182 MB；
- 启动方式：`startup.bat` → `vera_venv\Scripts\python app.py`，浏览器访问 `http://127.0.0.1:7860`。

## 2. 方案一：界面全面汉化（R1）✅ 已实施

### 2.1 汉化原则

1. **只改界面文案，不动任何推理逻辑与参数键名**（参数 JSON 键名 `Exposure2012` 等为模型训练用的协议名，保持英文原样，仅在旁边加中文显示名）；
2. 文案集中管理：新建 `ui/i18n.py`，所有界面字符串以常量/字典形式存放（便于后续二次校对或做国际化），`app.py` 不再散落硬编码文案；
3. 沿用现有组件，不更换 Gradio 版本。

### 2.2 汉化点清单（`app.py` 逐处核对）

| 位置 | 现状 | 汉化后 |

### 2.3 边界说明（明确不做）

- **模型输出的"分析文本"本身是英文**——这是 Qwen2-0.5B 的生成行为，不是界面文案，本方案不改模型（改它需要重训或接翻译器，均超范围）；
- 参数 JSON 内的键名（`Exposure2012` 等）保持原样，否则会破坏 `get_organized_dict` 的匹配。

### 2.4 验收标准

- 打开界面后 **所有可见控件（含下拉、提示 info、按钮、报错弹窗、进度条描述）均为中文**，无残留双语尾巴；
- 四条链路（自动/风格/参数/参考图）在汉化后回归测试仍全部跑通（文案改造不得引起事件绑定错位）。

## 3. 方案二：参数修图"滑轨 + 数值框"图形化界面（R4）✅ 已实施

### 3.1 现状与目标

| | 现状 | 目标 |
|---|---|---|
| 参数输入 | 一个 JSON 大文本框（38 个键手写） | 每个参数一个独立输入区域：**滑轨拖动 + 数值框直输**（Gradio `gr.Slider` 天生两者兼备），配中文作用说明 |
| 模式 | 仅 JSON | **可切换**：「图形输入模式」⇄「JSON 专家模式」，双向同步 |
| 参数说明 | 无 | 滑块下方 `info=` 显示中文作用说明与影响方向 |

### 3.2 交互设计

```
┌─ Tab 参数修图 ───────────────────────────────────────────────────────┐
│ 参数输入方式：  (•) 图形输入模式    ( ) JSON 专家模式      ← gr.Radio 切换
│
│ ┌ 图形输入模式容器（默认显示, visible=True） ──────────────────────┐
│ │ ▸ 折叠面板 1：光线调整（10 个滑块）                              │
│ │ ▸ 折叠面板 2：色温与整体色彩（4 个滑块）                          │
│ │ ▸ 折叠面板 3：特定颜色调整 HSL（24 个滑块，按 8 色 × 3 通道排列） │
│ │ [全部归零] [载入示例参数] [生成 JSON（供导出/对照）]               │
│ └──────────────────────────────────────────────────────────────────┘
│ ┌ JSON 专家模式容器（默认隐藏, visible=False） ────────────────────┐
│ │ [JSON 文本框 —— 与现在完全一致的 {"Key":{"value":..}} 格式]       │
│ │ [从滑块生成 JSON] [解析 JSON 到滑块]                              │
│ └──────────────────────────────────────────────────────────────────┘
│ [上传图片]  [开始参数修图]        →  [修图结果] + [模型分析文本]
└────────────────────────────────────────────────────────────────────────┘
```

要点：

1. **每个参数一个 `gr.Slider(minimum=-100, maximum=100, step=1)`**：滑轨可拖动 → 数值可同步；**数值框可直接敲数字回车** → 滑块跟着移动（Gradio Slider 组件自带此双向行为，无需额外代码）；
2. 滑块 label 显示「中文名（英文键名）」，例如「曝光度 Exposure2012」——中文名给用户读，英文键名供对照 JSON；`info=` 显示作用说明（见表 3.3）；
3. **模式切换时双向同步**：
   - 切到 JSON 模式：用当前 38 个滑块值自动生成 JSON 文本填入编辑器；
   - 切到滑块模式：**尽力**解析 JSON → 批量写回 38 个滑块；键缺失按 0 处理，含未知键则弹中文提示（未知键会被推理端忽略，不阻塞）；
   - **⚠ 解析失败绝不阻断切换**（2026-11-04 修复的实测 bug）：手工编辑的非法 JSON 或空编辑器曾在切换时抛 `gr.Error`，导致该事件的全部输出（含面板可见性）被跳过，表现为"滑轨无法加载"。现行为：解析失败 → 弹黄色警告「无法解析 JSON（保留滑块原值，可点『解析 JSON 到滑块』修正）」→ 面板照常切换。提交语义不受影响（提交时按当前模式的真实数据源取参）。回归用例：`tests/repro_invalid_json_switch.py`（case A/B/B2/B3/C 全通过）；干扰排查脚本：`tests/repro_mode_switch.py`（走真实 HTTP 队列）；`routes.py` 的 `HTTP_422_UNPROCESSABLE_ENTITY` 提示为 gradio 依赖的良性 DeprecationWarning，可忽略；
4. 三个便捷按钮：「全部归零」（全部滑块置 0，等价于当前页面默认态）、「载入示例参数」（读取 `data_samples/param.json`，即曝光+30 / 色温-40 / 饱和+30 的示例组合）、「生成 JSON」；
5. 提交时：图形模式下由滑块值组装成 JSON 字符串 → **走与现在完全一致的 `param_handler`/`Infer_Param_Dataset` 链路**（零推理改动），JSON 模式则原样提交 → 保证改造纯属于 UI 层。

### 3.3 参数定义表（新建 `ui/params_def.py`，共 38 项）

> 数据结构：`PARAM_DEFS = {"键名": {"name": "中文名", "desc": "作用说明", "min": -100, "max": 100, "group": 1|2|3}}`
> 说明均为"**正数→ / 负数→**"格式，让用户明确方向感。范围统一 -100~100（提交前内部 ÷100 归一化为 -1~1）。

**第 1 组 · 光线调整（Light Adjustment，10 项）**

| 键名 | 中文名 | 作用说明（info 文案） |
|---|---|---|
| `Exposure2012` | 曝光度 | 整体提亮/压暗画面。正值增加曝光使照片变亮；负值减少曝光、变暗 |
| `Contrast2012` | 对比度 | 增强画面明暗反差。正值对比更强、更"硬"；负值更柔和、发灰 |
| `Highlights2012` | 高光 | 单独调整画面最亮区域。负值找回过曝高光细节；正值压暗后高光更突出 |
| `Shadows2012` | 阴影 | 单独调整画面最暗区域。正值提亮暗部、找回阴影细节；负值暗部更沉 |
| `Whites2012` | 白色色阶 | 调整接近纯白的像素。正值白场更通透；负值抑制过白的死白 |
| `Blacks2012` | 黑色色阶 | 调整接近纯黑的像素。负值黑场加深、画面更"实"；正值黑场发灰 |
| `ParametricShadows` | 参数曲线 · 阴影区 | 类 PS 曲线中的阴影分段。正值提亮阴影段；负值压暗 |
| `ParametricDarks` | 参数曲线 · 暗调区 | 类 PS 曲线中的偏暗分段。正值提亮；负值压暗 |
| `ParametricLights` | 参数曲线 · 亮调区 | 类 PS 曲线中的偏亮分段。正值提亮；负值压暗 |
| `ParametricHighlights` | 参数曲线 · 高光区 | 类 PS 曲线中的高光分段。正值提亮；负值压暗 |

**第 2 组 · 色温与整体色彩（Color and Temperature Adjustment，4 项）**

| 键名 | 中文名 | 作用说明 |
|---|---|---|
| `IncrementalTemperature` | 色温（冷暖） | 正值偏黄暖调；负值偏蓝冷调 |
| `IncrementalTint` | 色调（绿↔品红） | 正值偏品红；负值偏绿。常用于校正或强化环境色 |
| `Vibrance` | 自然饱和度 | 智能加饱和：优先增强低饱和色，肤色不易过火 |
| `Saturation` | 饱和度 | 全体颜色饱和度平移。正值更艳；负值趋近黑白 |

**第 3 组 · 特定颜色调整（Specific Color Adjustment / HSL，8 色 × 3 通道 = 24 项）**

| 通道 | 键名模式 | 中文说明 |
|---|---|---|
| 色相 Hue | `HueAdjustment{颜色}` | 把该颜色往邻近色上偏移。正值/负值方向不同（如红→偏橙 或 偏紫） |
| 饱和 Saturation | `SaturationAdjustment{颜色}` | 只增减该颜色的浓淡程度 |
| 明度 Luminance | `LuminanceAdjustment{颜色}` | 只提亮/压暗该颜色的亮度 |

8 个颜色项逐一列出：

| 颜色 | 中文名 | Hue 说明（Sat/Lum 同理按通道套用） |
|---|---|---|
| `Red` | 红 | 红色区域色相：正→红偏洋红，负→红偏橙 |
| `Orange` | 橙 | 橙色（含肤色）区域：正→橙偏红，负→橙偏黄 |
| `Yellow` | 黄 | 黄色区域：正→黄偏红，负→黄偏绿 |
| `Green` | 绿 | 绿色区域：正→绿偏黄，负→绿偏青 |
| `Aqua` | 青 | 青色区域：正→青偏蓝，负→青偏绿 |
| `Blue` | 蓝 | 蓝色区域：正→蓝偏紫，负→蓝偏青 |
| `Purple` | 紫 | 紫色区域：正→紫偏蓝，负→紫偏洋红 |
| `Magenta` | 洋红 | 洋红区域：正→洋红偏紫，负→洋红偏红 |

注意事项与对策：

| # | 风险点 | 对策 |
|---|---|---|
| P1 | 38 个滑块事件量大 | 文案/事件一次性构建；滑动不实时回写 JSON（避免事件风暴），同步在「切换模式 / 生成 JSON 按钮 / 提交时」三处触发 |
| P2 | Gradio 6 中 38 个组件的 inputs 位置映射易错（前车之鉴见原方案 §实施结果摘要第 3 条） | 数据统一打包为列表：`sliders = [s1..s38]`，handler 用 `*args` + 索引常量取值，并单测键位对齐 |
| P3 | JSON 模式手写的键名大小写错误会被静默忽略 | 解析时对照 `PARAM_DEFS` 给出中文提示「未识别的键：xxx（已按 0 处理）」 |
| P4 | 「特定颜色」24 个滑块占屏 | 用 `gr.Accordion(open=False)` 默认折叠 + 两列布局（`gr.Row` + `gr.Column`） |
| P5 | 全 0 提交（三组全为 0） | 依 `get_mask_from_path` 语义**允许提交**（模型将不注入任何参数潜变量，相当于让模型自拟方案由提示注入为 0），但在提交时弹出提示确认，避免用户误以为"全 0 也有效果" |
| P6 | 切换事件中的数据解析失败会连带拖垮可见性切换（**已实测踩坑**：专家模式手工 JSON 解析失败 → `gr.Error` → 41 个输出全跳过 → "滑轨无法加载"） | **模式切换处理器内任何解析都不允许抛错**：尽力解析，失败降级为 `gr.Warning` 并保留滑块原值；阻断式报错只允许出现在显式按钮（「解析 JSON 到滑块」）与提交入口。回归测试 `tests/repro_invalid_json_switch.py` 需保持通过 |

### 3.5 验收标准

- 38 个参数均可：拖滑轨 → 数值变化；数值框输入 → 滑块移动；每个滑块下方显示中文作用说明；
- 图形模式 ⇄ JSON 模式可往返切换且数值一一对应不丢失；
- 用滑块模式提交一张样例图，结果与手写等价 JSON（键值完全相同）的 CLI `--mode param` 输出结果一致（排除采样随机性，`temperature=0` 复跑）；

## 4. 方案三：打包成可安装程序（R2 + R3，合并实施）

需求 R2（可安装 + 体积小）与 R3（免 Python）必须一并设计，因为安装包的层叠方式同时决定了两者。

### 4.1 技术选型对比（先定路线）

| 方案 | 体积 | 免 Python | Gradio/torch 兼容风险 | 可维护性 | 结论 |
|---|---|---|---|---|---|
| A. PyInstaller / Nuitka 冻结单目录 | 同量级 | ✅ | **高**：gradio（含前端静态资源、本地文件服务）与 torch DLL 打包极易缺件，历史坑多 | 差，每次改代码全量打包重验 | ❌ 不采用 |
| B. **嵌入式 Python + 精简 site-packages + Inno Setup 安装器** | 同量级且可精确控制 | ✅（安装包自带 Python） | 低：运行形态与现在完全一致（目录 + 解释器），可先用现有 venv 直接验证 | 好：代码改动后只需重新打安装包 | ✅ **采用** |
| C. 要求用户装 Python（现状） | 最小 | ❌ | — | — | 与 R3 冲突，淘汰 |

> 内嵌 Python 后"推理引擎 = 一个磁盘目录"，与当前开发态零差别 —— **这是把 R3 的风险降到最低的关键**。

### 4.2 安装后的目标目录结构

```

├─ VeraRetouch.exe                                ← 启动器（见 §4.6，双击即开）
├─ runtime\
│  ├─ python.exe / python312.dll / *.pyd          ← 嵌入式 Python 3.12（免安装）
│  ├─ python312._pth                              ← 需手工解开 Lib\site-packages 行（§4.4）
│  └─ Lib\site-packages\                          ← 精简后的依赖（§4.3）
├─ app\
│  ├─ app.py、inference.py、llava\、model\、data\、configs\、ui\ …   ← 本项目源码
│  └─ (Android 工程目录 ml-veraretouch\ 与。git 类文件不随包安装)
├─ checkpoints\{VeraRetouch, encoder_renderer.pth} ← 首次启动后生成（§4.5）或离线包安装
├─ gradio_outputs\

```

### 4.3 体积优化（R2 核心）

**基线实测：当前 `vera_venv` = 1.3 GB。** 优化分四步，每一步后跑导入冒烟测试（阶段 0 已有验证命令）防止删过头：

① **从 requirements.txt 全新干净安装**（删掉历史 venv，避免累积垃圾）：
```bash
python -m venv vera_venv_pack --without-pip && (引导 pip 后)
vera_venv_pack\Scripts\pip install -r requirements.txt --no-cache-dir --only-binary :all:
```
（`--only-binary :all:` 确保不拉源码构建产物；torch CPU 随 peft 自动装入，与现环境一致）

② **删除推理链不必需的依赖**（本次已逐文件核对 import 关系得出的依据）：

| 包 | 结论 | 依据 |
|---|---|---|
| `matplotlib`、`scikit-image` | **可删（约省 150+ MB）** | 仅被 `data/data_utils.py` 引用，而该文件在推理链（app.py→infer_dataset / utils.py→model）中**无任何导入者**。保险起见将 `data/data_utils.py` 顶部两句 import 改为函数内惰性导入/try-except，测通后移出 requirements |
| `peft` | 疑似仅作"拖 torch 进门"的依赖 | 属 transformers 生态圈可能被 llava 间接引用，**保留**（后续可用 `pip install torch --index-url ... --no-deps` + 删 peft 再验，省约 10 MB，列为选测项） |
| `diffusers`、`timm`、`transformers`、`gradio` 等 | 保留 | `retouch_render.py` / MobileCLIP 塔 / 界面必需 |

③ **装完后清冼 site-packages**（脚本自动执行，删的都是"死的"文件）：
- `tests/`、`test*/`、`*.dist-info\RECORD` 之外整目录 dist-info、`*.pyi`、`Scripts/` 内不再需要的 exe、各包 `docs/`、`LICENSE*`、`*.c/.h` 残留；
- `numpy` 的 tests 与几千个 `.html` 文档；
- 每删一类跑一次 `python -c "import torch, cv2, transformers, timm, diffusers, gradio, yaml; import inference, utils"`。

④ **预估**（最终以打包脚本输出为准，本节为决策依据）：

| 项 | 原始 | ①–③ 精简后预期 |
|---|---|---|
| site-packages + runtime | ~1.3 GB | **≈ 1.05 – 1.15 GB** |
| 安装包（Inno Setup LZMA2 固实压缩/最大档，典型压缩率 52–60%） | — | **≈ 520 – 650 MB**（**目标 < 700 MB**） |
| 模型权重 | 2.3 GB | **不进安装包**（见 §4.5），首启下载 / 离线权重包 |

> torch（含 DLL）是压缩后的大头，占据包体积的绝大部分，属于物理下限，不再压榨代码侧可砍的部分。

### 4.4 免 Python 实现（R3 核心）

1. 下载官方 **python-3.12.x-embed-amd64.zip**（约 11 MB）→ 解压到安装目录 `runtime\`；
2. **必改**：`python312._pth` 中取消 `Lib\site-packages` 与 `import site` 两行的注释，否则整个 site-packages 目录不可见（嵌入式 Python 默认关闭 site 机制，这是"打包后 ModuleNotFoundError"最常见的根因）；
3. 用 runtime 里的 python 执行 §4.3 的 pip 安装（嵌入式包自带领先 pip 的引导方式：`python -m ensurepip --default-pip` 或直接 `python get-pip.py`）；
4. 结果：目标机器**零 Python 环境要求**，卸载时随 uninstall.exe 删除 runtime；
5. 版本锁定：嵌入式 Python 版本必须与依赖编译目标一致（3.12），与现有验证环境同构，无新增兼容风险。

### 4.5 模型权重的三种分发形态（安装包瘦身的关键）

| 形态 | 安装包体积 | 使用场景 | 说明 |
|---|---|---|---|
| **形态 1（推荐）：安装包不含权重，首次启动引导下载** | ~600 MB | 大多数用户 | 首次启动时界面显示一键下载（或启动器自动），从 HF 镜像 `hf-mirror.com` 拉 2.29 GB 主模型 + 182 MB 渲染器，支持断点续传；下载前界面提示"约 2.3 GB，请保持网络" |
| 形态 2：离线权重包（.7z/.exe）与安装包分别下载 | 安装包 ~600 MB + 权重包 ~2.3 GB | 无法联网机器 | 提供两个 exe，权重包装到运行目录即被识别 |
| 形态 3：合并全量安装包 | ~2.2 – 2.6 GB | 局域网一键分发 | 可选产出，同一 `veraretouch.iss` 用 `#define` 开关切换 |

### 4.6 启动器与首次下载器

- `VeraRetouch.exe`：小启动器（可由 Inno 打包时用批处理转 exe：`Ve`,或用一个 100 行的 C/small 脚手架），职责：
  1. 检查 `checkpoints\VeraRetouch\model.safetensors` 是否存在 → 缺失则启动后台下载（`huggingface_hub.snapshot_download`，`HF_ENDPOINT=https://hf-mirror.com`，日志落盘）→ 完成校验文件大小；
  2. 启动 `runtime\python.exe app.py --model-path checkpoints\VeraRetouch`；
  3. **先轮询探活端口 `127.0.0.1:7860`，探活成功后才拉起浏览器**——原因：`app.py` 现为「先加载模型（约 1–2 分钟）→ 后启动 HTTP 服务」的启动顺序，若立刻开浏览器只会得到"无法访问"报错页。探活期间启动器可用小窗口或控制台提示「模型加载中…」；
  4. **关闭启动器窗口即退出程序**（浏览器标签页仍开着时会立刻显示"连接失败"，属预期行为；可加"最小化到托盘"为后续项）。

> **已确认**：安装后的界面载体 = 本地浏览器打开的 Gradio 页面（表层是 Web 技术但完全运行在 127.0.0.1，不联网）；不采用 pywebview 独立窗口方案，理由：零新增依赖（pywebview 需引入约 20–30 MB 且老机器可能缺 WebView2 运行库）、零新增兼容风险，且与现有已验证的界面完全同构。

### 4.10 GPU 优先模式（检测到独立显卡时的分流，兼容 CPU-only 与 N 卡两类机器）——G2/G3 代码层已实施；G1/G4 属安装器分流，随 P3 实施

> 已确认决策（2026-11-04）：应用需同时兼容「仅 CPU」与「存在独显」两类机器，检测到 N 卡时启用 GPU 优先模式。

**4.10.1 已天然支持、无需改动的部分**（阶段 1 CPU 化即为设备自适应写法）：

| 逻辑 | 现状 | GPU 机器表现 |
|---|---|---|
| 设备选择 `torch.cuda.is_available()` | `app.py:38` / `inference.py` 同构 | 自动命中 GPU，零修改 |
| 精度 `--dtype auto`：GPU→bf16、CPU→fp32 | `app.py:40/42` | 自动 bf16 |
| 数据搬运 | 全部 `.to(device)`，无残留 `.cuda()` | 已在阶段 1 清理 |
| CPU 专属设置（`set_num_threads`、`num_workers=0`、CPU 自动 chunk） | 均有 `device.type=="cpu"` 条件 | 不影响 GPU 分支 |
| 界面设备徽标 | 「当前运行设备：cuda / bfloat16」 | 自动显示 |

**4.10.2 四处真实差异（"不止是依赖差异"）：**

| # | 差异点 | 内容与对策 |
|---|---|---|
| G1 | **torch 必须双版本分发** | requirements 中 peft 自动拉取的 PyPI 版 torch 即 CPU 版；GPU 需 `download.pytorch.org` 的 CUDA 版 wheel（约 2.5 GB+）。两者同名不可共存于同一 site-packages → 不能做成"单包内自动二选一"，必须安装器向导阶段分流（见 4.10.3）。**CPU-only 用户不得被迫下载 CUDA torch**（维持 <700 MB 目标） |
| G2 | **dtype 按算力分级** | bf16 需要算力 ≥ 8.0（RTX 30 系起）才有原生加速；Pascal 老卡（GTX 10 系）可能报运算不支持或异常慢。`resolve_device_and_dtype` 增加判断：`major >= 8` → bf16，否则 → fp32（仍走 GPU）。约 5 行改动 |
| G3 | **GPU 下渲染 chunk 按显存自适应（现有逻辑有 OOM 风险）** | 现状：CPU 恒开 `chunk=262144`，GPU 反而不分块（`chunk=-1`）；渲染 1707×1280 大图不分块需一次性 4.47 GB 激活显存，叠加 2.3 GB 权重 → 6–8 GB 卡跑大图会 OOM。改为按 `torch.cuda.get_device_properties().total_memory` 自适应：显存 ≥ 12 GB 允许 `chunk=-1`，否则同 CPU 一样开 `262144`。约 10 行改动 |
| G4 | **"独显"限 NVIDIA（第一期）** | Windows 无可用 ROCm torch（A 卡）、DirectML 是另一套栈（torch-directml，兼容性未知，列为后续增强项）。检测逻辑 = `nvidia-smi` 存在且驱动版本达标（CUDA 轴对应，通常 ≥ 550）→ GPU 模式；否则一律 CPU 模式。**安装器向导文案必须写明"GPU 加速仅支持 N 卡"**，防止 A 卡用户误装 |

**4.10.3 安装器向导分流设计：**

```
向导阶段 1：执行 nvidia-smi 检测（Inno [Code] 脚本）
├─ 无 N 卡 / 驱动过旧 / A 卡 → 直接走 CPU 标准安装（不出现 GPU 选项）
├─ 检测到 N 卡 + 驱动达标 → 出现二选一（默认勾选 GPU）：
│    [ ] 标准安装（CPU 运行，安装后也可经「GPU 扩展包」升级）
│    [✓] GPU 加速安装（需联网，自动追加下载 CUDA 版 torch 并覆盖安装到
│        runtime\Lib\site-packages，版本号与 CPU 版严格一致以避免混装）
│    离线场景 → 提供「GPU 加速扩展包.exe」（形态 2 的姊妹包），面板同款覆盖安装
└─ 运行期兜底：启动时打印设备徽标"GPU 优先模式 (RTX xxxxx, 显存 xx GB)"，
   若 CUDA 初始化失败自动回退 CPU 并提示（torch 能 import 但驱动故障时的兼容路径）
```

**4.10.4 代码改动汇总（仅 2 个文件、约 15 行，不动推理链结构）：**

`app.py`（`resolve_device_and_dtype` + chunk 笔路）、`inference.py`（同步同款 dtype/chunk 分级逻辑）；界面设备徽标文案微调。验收标准：

- CPU-only 机、N 卡机、A 卡机三类机器各跑一次安装向导：分流正确、A 卡机器看不到但也不会误装 GPU 选项；
- N 卡机（≥12 GB 显存）大图跑通且无 OOM；6–8 GB 卡自动开启 chunk 跑通；
- 装了 GPU 扩展包的机器 `torch.version.cuda` 非 None、速度显著优于 CPU 版；卸载扩展包恢复 CPU 版后功能无回退。
